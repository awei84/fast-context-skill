## 一句话目标

把已有的 `fast-context-mcp`（纯 Node、MCP 形态）**复用其核心代码**，做成一个 **Skill + CLI** 形态的新项目，服务 Claude / agent 生态。**不是推倒重来，是加一层 CLI 入口 + 一个 SKILL.md。**

---

## 一、这个项目是怎么来的（背景）

### 1.1 母项目

- 母项目：`fast-context-mcp`（本地路径 `/Users/awei84/开源项目/fast-context-mcp`）
- 形态：纯 Node ESM 的 MCP server（stdio transport），`npx -y fast-context-mcp` 一键启动，零系统依赖
- 核心能力：逆向 Windsurf 的 SWE-grep 协议（Connect-RPC + Protobuf），调 Devstral 模型做多轮 agentic 代码搜索，本地跑 bundled ripgrep，返回文件路径 + 行号 + grep 关键词
- npm 双包发布：`fast-context-mcp` 和 `fast-cxt-mcp`
- **母项目继续维护，不动、不弃。** 本项目是它的「另一种形态」，不是替代。

### 1.2 触发点

社区里 `ferstar/fast-context` 把同类工具改成了 **Python CLI + Skill** 形态。由此引发讨论：我们要不要也做 Skill？经过几轮评估，结论是 **值得做一个 Skill + CLI 版本，但用 Node 复用现有代码，不用 Python。**

---

## 二、关键决策（务必遵守）

### 决策 1：不做「本地 Semble 兜底」❌

最重要的一条。`ferstar` 版本引入了 `semble`（MinishLab 的本地语义搜索库）做「远程挂了降级到本地」。**我们明确不做这个。** 理由：

- **触发场景窄**：只在远程长时间全挂时才触发，多模型重试已能磨平偶发抖动，留给本地兜底的夹缝极小，一年遇不到几次。
- **摧毁「轻量零依赖」定位**：semble 是 Python 库 + tree-sitter + 16M 模型下载 + 本地索引缓存。引入它，我们纯 Node、npx 一键、零系统依赖的最大优势直接破功。
- **结论**：semble 本身是好库（Model2Vec + BM25 + RRF，NDCG@10 0.854，CPU 250ms），但**和我们的栈/定位不匹配**。不是它烂，是不合适。

### 决策 2：CLI 用 Node，复用母项目代码 ✅

母项目的核心逻辑早已与 MCP 壳解耦（`core.mjs` 的 `searchWithContent`、`buildFastContextSearchTool`）。CLI 化只需写一个新入口：把「MCP 协议输入」换成「argparse/命令行参数输入」，把「结构化返回」换成「`console.log` 格式化输出」。底层 `core.mjs / executor.mjs / protobuf.mjs / extract-key.mjs / directory-scorer.mjs / project-path.mjs` 基本原样复用。

### 决策 3：Skill 只做薄包装 ✅

`SKILL.md` 本质是 markdown，告诉 Claude「何时调用、用什么参数跑哪条命令」。命令形如：

```bash
npx -y <包名> search --query "..." --project .
```

Skill 正文按需加载，常驻 token 几乎为零。母项目 CLAUDE.md 里那套「工具优先级 / 推荐参数 / 禁止猜测代码位置」的搜索策略，正是 SKILL.md 的好素材。

### 决策 4（可选，待定）：多模型 fallback + 重试退避

`ferstar` 版本里**真正有价值**的部分（与 Skill 无关）：远程某模型不可用/限流时自动切下一个模型 + 指数退避重试。成本低、不引依赖、不碰轻量定位、能感知地提升鲁棒性。**母项目和本项目都值得加。** 本项目可优先纳入。
（注意：这条是「多模型重试」，不是「本地 Semble 兜底」——两者要分清，前者要做，后者不做。）

## 三、为什么是「新项目」而不是改母项目

- 母项目的护城河是 **跨客户端**（Cursor / Claude Desktop / 任意 MCP 客户端都能用）。MCP 形态必须保留。
- Skill 形态是 Claude 生态专属。两种形态目标用户不同，分仓库各自演进更干净。
- 一份核心代码、两种形态：母项目出 MCP，本项目出 CLI + Skill。后续可考虑把 `core` 抽成共享包，避免双份维护（见「五、待办」）。
